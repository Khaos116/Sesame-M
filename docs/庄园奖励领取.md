# 庄园奖励领取（道具/美食）改动记录

需求：完成庄园任务后自动领取 1–3 个美食，饲料奖励保持原逻辑。类型判断以
`awardType` 为准，不按数量区分饲料和美食。

现状（2026-09-26）：道具链路防中断、字段校验、同轮补领已实现并回归；美食
`awardType` 服务端真值待结合任务列表与领取响应确认，在此之前不认定美食领取已修好。
一行摘要见 `CHANGELOG.md` 同日三条，本页记推理、取舍和待办。

## 已确认的事实

- 饲料任务链路（`listFarmTask` → `receiveFarmTaskAward`）对 FINISHED 全量领取，
  不按奖励类型和数量过滤；饲料超上限只拦 `ALLPURPOSE`，非饲料不受库存门限影响。
- 道具链路（`listToolTaskDetails` → `receiveToolTaskReward`，受"收取道具奖励"开关控制）
  曾有两个中断点：未知 `awardType` 使 `ToolType.valueOf` 抛异常 abort 整轮，后续待领全跳过；
  `listFarmTool` 失败时 `farmTools` 为空导致 NPE abort。均已修。
- GR2026/Sure-Xu 与 M 旧逻辑同构；AG 对未知道具类型直接跳过（与 M 的"直接领"相反）。
  三家 fork、git 历史、公开搜索均无美食 `awardType` 真值——静态侧已查尽。

## 改动

1. `AntFarm.receiveToolTaskReward`：未知非空类型跳过"满额"判断直接领（原先 abort 整轮）；
   `farmTools` 为空同理；领取失败记标题+类型+数量+memo。
2. P2 校验：空 `awardType` / `awardCount<=0` / 空 `taskType` 视为数据缺失直接跳过，
   不发无效请求；仅非空未知类型直接领。区分"合法的新类型"和"数据缺失"。
3. `AntFarm.run()` 结尾加 `step("道具奖励补领")`：本轮动作（做任务/喂鸡等）翻转的新可领
   道具同轮领走，不等下次运行。同"收取道具奖励"开关。
4. `AntFarm.receiveFarmTaskAward`：只加失败留痕
   （`饲料任务⚠️领取失败[标题]#类型[awardType]数量#memo#resultCode`），行为未动。
5. 回归 `checks/check_antfarm_tool_reward.py`（已注册进 `AGENTS.md` 清单）：抽取真实
   `receiveToolTaskReward`/`receiveFarmTaskAward`/`pendingAward`/`add2FoodStock` +
   真实 `ToolType`/`TaskStatus`/`FarmTool`，隔离 RPC 边界验证 7 组：
   未知类型直领不阻断后项、缺失字段零 RPC、满库存暂缓、失败留痕、重查领走本轮新完成、
   非饲料 1/2/3 满仓照领且不动饲料库存、饲料超限暂缓/装下照领，外加补领顺序断言。

## 待确认（唯一缺口）

美食 `awardType` 服务端真值及所属列表。确认归属及结果需结合目标美食任务的标题、
列表响应、奖励类型和领取响应综合判断，单行日志不能定案：

- `未知类型[X]#直接领取` → 仅说明道具列表发现 X 类型的待领奖励：
  X 是否为美食需对照任务标题/列表响应；该行打印在请求之前，是否领成功看后继的
  `领取道具🎖️[...]` 成功行或 `领取道具⚠️失败[...]` 行；
- `饲料任务⚠️领取失败[标题]#类型[X]...#memo[...]` → 在普通任务列表且本次领取失败，
  memo 说明拒因；
- 以上都没出现 → 无结论。还可能是开关关闭、任务未完成、当天完成标记跳过查询、
  或普通任务已成功领取（成功行是 `饲料领取🎖️`，与失败行分开看）。

取法：App 内日志页搜"未知类型"/"领取失败"，或手机
`sesame-M/log/<账号名>/` 当天 runtime 日志搜同样关键词。

确认后：把回归里的 `MEISHI_AWARD_PROBE` 换成真值；若走普通任务列表且需特殊领取参数，
再改对应路径（各分支条件与具体串值无关，替换即生效）。

## 明确未声称

- "未知类型允许发送请求"不等于"美食领取已实现"。
- 编译和已有回归通过只证明道具链路行为正确，不证明美食归属。
